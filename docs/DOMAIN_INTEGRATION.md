# 都市システム統合仕様 v0.2 — 交通以外にも共通計算を適用する

> **設計仕様（未実装・未計測）**。住民・建物・電力・水道・税・教育・物流等のFeature Issue #13〜#60を、同じイベント実行基盤へ接続するためのルール。共通の時刻・ID・状態遷移・容量処理は [RUNTIME_PROTOCOL.md](RUNTIME_PROTOCOL.md)、全般的な契約は [IMPLEMENTATION_SPEC.md](IMPLEMENTATION_SPEC.md) を正本とする。

## 1. 「集団計算」が向いているもの・向いていないものを分ける

都市機能の共通化では、すべてを人のIDで数える必要はない。

| 対象 | 計算の共有キー例 | 個別性の保存 | 更新を起動する条件 |
| --- | --- | --- | --- |
| 住民の生活 | 地区・職業・年齢帯・時間帯・予定の型 | CitizenId、世帯ID、予定出発時刻、目的地 | 曜日/日付・転職・転居・施設停止 |
| 入居と建物 | 建物用途・密度・土地の適性 | BuildingId、ParcelId、世帯ID、空き容量 | 建設完了・入居・転出・用途変更 |
| 商業・産業 | 生産レシピ・地区・稼働状態 | FirmId、在庫量、バッチ/貨物のID | 注文・欠品・完成・納品・営業切替 |
| 電力・水道・下水 | 接続成分・容量・利用時間帯 | 設備IDと系統、供給/需要量、対象建物 | 設備の停止/復帰・需要増減・配管変更 |
| ごみ | 地区・建物用途・排出原単位 | 地区/建物の蓄積量、回収車ID | 回収時刻・排出率変化・施設満杯 |
| 学校・医療 | 施設/地区/年齢層/需要区分 | StudentId、PatientId（発生時）、施設の定員 | 入学/卒業・発病/治療終了・施設停止 |
| 治安・消防 | 地区/時間帯/施設タイプ/発生率 | IncidentId、出動車両ID、対象建物 | 発生・出動・到着・鎮火 |
| 地価・汚染 | 地区/空間セル・基準値 | ParcelId/汚染セル・局所補正 | 交通/施設/天候/排出源の変更 |
| 都市財政 | 課税種類・地区・会計期間 | TransactionId、金額、対象・発生時刻 | 課税期間締切・支出・政策変更 |

**IDが必要なのは「誰が・どこへ・何をしたか」の同一性を保持する場合**。系統全体の電力量、地区の消費率、空気中の汚染量などの値は、数値集計として扱うのが自然。

ゲーム実体を必ず「一つのクラスオブジェクト」として作る義務はない。一方、適切な責務を持つオブジェクトを使用することも否定しない。**同じ処理を不要に繰り返さないこと**を重視する。

## 2. 時間的な集約を計算式として表現する

交通だけでなく、一定期間に発生する需要/供給/消費にも**途中経過を毎フレーム更新しない**考えを適用する。

たとえば、ある地区の1000世帯が同じ条件でごみを出す場合:

```text
lastUpdatedAt = t0
accumulatedAmount = A0
ratePerMs = r

時刻tで必要になった時:
A(t) = A0 + r × (t - t0)
```

- `r`は地区・世帯条件の共通計算から求める。世帯が増減した場合は**変更時刻でAを確定**し、そこから新しい率を使う。
- 容量限界が`C`なら、`r > 0`のとき`tLimit = t0 + (C - A0) / r`に満杯イベントを予約できる。時間が経過するたびに全世帯を走査する必要はない。
- 類似の方式を水道需要・電力需要・資源採取・貨物生産・燃料消費・施設利用に適用できる**場合がある**。非線形・イベント依存の機能は適切な区分で計算する。
- 端数を丸めた結果、資源や資金が消えたり増えたりしないよう、**固定小数点/整数の最小単位と余り**を保持する。計算方式は各機能の性質に合わせて検証して決める。

このモデルは**予測が正しい区間だけ成立する**。途中で火災、停電、価格変更、政策変更があれば時刻を切って再アンカーする。

## 3. Domain Changeと依存の伝播

Domainが自分のStateを変更したときは「変更差分」と「何が無効になったか」をProcess内部の明示契約で伝える。

```text
道路敷設・区画変更
    → NetworkRevisionChanged / ParcelEligibilityChanged
    → 建設可能条件 / 土地需要を更新
    → BuildingConstructionCompleted
    → BuildingCapacityChanged
    → HouseholdMovedIn
    → PopulationDistrictChanged / ElectricityDemandChanged
    → TransitDemandChanged / BudgetTaxBaseChanged
```

処理手順:

1. **原因**となるコマンド/イベントが、所有Domainの状態を一度だけ確定。
2. 更新対象のID/敷地/設備/地区を差分として発行。変更のない対象への全件通知を避ける。
3. 各Domainはこの差分から再計算が必要な共有集団を特定し、イベント/期限を失効・再予約する。
4. 派生した状態変更は同時刻の後続`microRound`/phaseで伝播する。再帰的な直接呼出で無限に通知を連鎖させない。
5. 各変更には`CauseId`/状態のrevisionなどを付与し、同一の確定変更を二度受け取っても二重計上しない仕組みを持つ。

**変更イベントを全世界へブロードキャストしない。** 地区・系統・建物・区間など影響を特定できる逆引き索引を持つ。

## 4. 容量と保存量はドメインごとに管理する

| Domain | 必ず守る不変条件 | 通過/入居に相当する操作 |
| --- | --- | --- |
| 建物 | 居住世帯/職場枠が定員を超えない | `OccupancyRequested→Admitted/Wait` |
| 学校 | 在籍者数が学校定員を超えない | `EnrollmentRequested→Enrolled/Waiting` |
| 病院 | 病床・診療枠・救急車を重複使用しない | `CareRequested→Assigned/Waiting` |
| 交通 | 道路/車両/改札/競合領域の容量と進路を守る | `MoveRequest→Allowed/Wait/Transition` |
| 電力 | 発電/系統供給量と需要割当の整合を守る | `SupplyRebalanced→Available/Unavailable` |
| 水道/下水 | 取水・供給/排水・処理が能力を超えない | `DemandChanged→AllocationChanged` |
| 物流 | 在庫の生成、輸送中、納品・消費を二重計上しない | `ShipmentRequested→Reserved/Delivered` |
| 財政 | 決済済の取引IDを二度記帳しない | `TransactionApproved→LedgerPosted` |
| 汚染・資源 | 発生/吸収/移送/採取の数量収支が合う | `EmissionPosted`/`ExtractionCommitted` |

共通の`CapacityLedger`は**原子性・予約・解放の仕組み**を再利用する契約。建物に入居することと車が交差点へ進入することの**ゲームルールまで同一視しない**。Domainごとの判定器を移譲して使う。

## 5. 住宅→交通→雇用の縦断フロー

```text
区画を指定
   ↓
建物が建つ（建物ID・定員）
   ↓
世帯が入居（世帯IDと住所・容量予約）
   ↓
市民に仕事/学校の目的地を割り当てる
   ↓
同じ条件の市民集団から通勤/通学需要を作る
   ↓
IDの出発時刻と目的地を残して移動集団へ編成
   ↓
道路・歩道・駅などの境界でState遷移
   ↓
目的地の施設に到着、所属Stateを変更
   ↓
施設の稼働/売上/税収/公共サービス需要が変化
```

- **目的地はIDごとに必要**。集団で通勤率を計算しても、誰がどの建物に勤務し、いつ到着したかを失わない。
- **住民の所在と施設への所属は別の属性**。職場に在籍していても、現在位置は通勤中の場合がある。
- 建物の閉鎖などで予定到着先が無効になれば、影響するTripIdだけ失効させ、待機・新しい目的地・再ルーティングに遷移。
- 最初から現実の全行動を再現する必要はない。**遊びに直結する入居・就労・移動・供給**を優先し、複雑な行動特性は後から追加する。

## 6. 周期処理とイベント処理は併用してよい

すべての事象をイベント化するのは適切ではない。

- **イベント型**: 信号変更、到着、建設完了、事故、出生、入学、満員、停電、納品、救急出動。
- **境界時刻で積分**: 水/電力の需要蓄積、燃料消費、ごみ蓄積、税収の計算基礎、施設の劣化等。
- **低頻度バッチ**: 地価・満足度・需要・地区別汚染場・長期人口統計。時刻と影響区域を記録し、集団ごとに更新する。
- **描画時だけ**: 見える住民の姿勢・視覚的な走行曲線、地図オーバーレイなど。論理結果を変えない。

「遠くは粗く、近くは細かく」は**処理方法の選択**であり、電力や税金までカメラ位置によって変動させる規則ではない。

## 7. ゲームプレイとして必要な情報を返す

最初から専門シミュレーションへ偏りすぎず、プレイヤーが自分の行動で結果を改善できる情報を優先する。

- 区画需要、空き住居、就労可能枠、道路混雑、電力/上下水の供給不足、税収/支出、地価/満足度等を **Processが集約して `CityView` に渡す**。
- 危機が起きると、要因・影響区域・必要な対応候補を表示できるよう `CauseId` と影響ID集合/地区を維持する。
- UIはプレイヤーができる操作のプレビューや表示を担当し、建設・資金・サービス容量の最終判断を持たない。
- 量・指標の根拠が説明できない更新則を増やすより、まず **同じ入力で同じ結果を再現できる最小のモデル**を成立させる。

## 8. テストと性能の確認方法

1. 同じ1000世帯からごみ需要を1日分積分して、毎秒更新版と結果を比較する。世帯数が途中で変わる場合は変更時刻で再アンカーする。
2. 建物定員100に対して101世帯が同時入居要求しても、100だけ受理・1は待機し人口・住所を二重計上しない。
3. 停電により建物の稼働が停止し、住民の目的地/税収が必要な差分だけ更新される。
4. 商品100個生産、40個発送、20個消費の場合、残在庫・輸送中・消費済みの各数量が一致する。
5. 同じ世界seed・入力・予定イベントで、カメラを動かしても人口・税収・交通・インフラ・施設稼働が同じ。
6. 規模1万/10万/100万IDで、各更新方式のイベント数・再計算地域数・メモリ/GC/CPUを測る。

各機能の**具体的な数式・閾値・ゲームバランス値**（税率/学齢/電力単位等）はこの共通契約で先に固定しない。実装とプレイテストを経て、関連Feature Issueへ入力/出力/範囲と併せて記録する。
