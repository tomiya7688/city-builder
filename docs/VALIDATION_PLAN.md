# 検証計画 v0.2 — 正しさと軽量性を切り分けて測る

> 対象: [#3](https://github.com/tomiya7688/city-builder/issues/3)、[#61〜#66](https://github.com/tomiya7688/city-builder/issues)。**試験設計であって実測結果ではない**。ランタイム契約は [RUNTIME_PROTOCOL.md](RUNTIME_PROTOCOL.md)、交通の試験シナリオは [TRAFFIC_VERTICAL_SLICE.md](TRAFFIC_VERTICAL_SLICE.md)。

## 1. まず正しさを検査する

全試験は描画なしのProcessだけで実行できること。固定seed、時刻、イベント列、生成したID集合を記録する。

| ID | 最小シナリオ | 検査する条件 |
| --- | --- | --- |
| C01 | 1000IDを10集団に分類→分割→統合 | 同じIDが重複せず、総ID集合が保存 |
| C02 | 共通歩行モデルの3人が5/6/7秒に到達 | 5秒で全員を到着済みにしない、時刻順に分岐 |
| C03 | 進入容量100に1000IDが要求 | 許可100/待機900。退出/再試行後もID集合が保存 |
| C04 | t=7に青と入場が同時刻 | 条件変更後に入場判定し、同一実行で再現 |
| C05 | 横断中に赤、車が競合領域へ要求 | 人は通過継続・車は競合解放までWait |
| C06 | t=2で12秒到着予測を8秒へ短縮 | 条件変更時に位置を再アンカーし早いイベントを予約 |
| C07 | t=2で8秒到着予測を12秒へ延長 | 旧イベントを失効し、誤到着しない |
| C08 | 交差点を閉鎖/迂回 | 閉鎖経路の旧予約を採用せず、IDが消えない |
| C09 | カメラ0回移動と100回移動で同じ入力を実行 | 正規WorldStateのハッシュと最終到着が一致 |
| C10 | 同時刻イベント中に停止要求、セーブ、ロード | 完了した処理境界から再開し同じ順序・状態を得る |
| C11 | 世帯1000・ごみ発生率が途中で変更 | 毎秒更新の参照実装と積分結果が許容誤差内で一致 |
| C12 | 住宅定員100に101世帯の同時入居 | 入居100/待機1、二重住所・定員超過なし |
| C13 | 生産・発送・消費・税の会計処理 | 在庫・現金の元帳が二重計上しない |
| C14 | 外部から無効なState・存在しない区間への要求 | Invalidを返し、正規状態の変更なし |

### Property / Metamorphic testの候補

- 論理結果は **UI描画の有無、カメラの位置、FPS** に依存しない。
- 同じ集団を必要以上に2つへ分割しても、ルールが等価なら最終的な論理結果は同じ（集団IDや内部イベントsequenceの違いは比較対象から除外する）。
- セーブして読み戻しても時刻・状態・予約残量と、その後の結果が一致する。
- ランダムな道路変更・信号イベント・ID集団分割を繰り返しても、ID集合・容量・状態整合が壊れない。

**比較ハッシュ:** UIキャッシュや集団の内部配列順は除き、EntityIdの安定順で正規状態・論理時刻・施設/容量/財政を直列化して得る。乱数状態やイベント予約は別の再現ハッシュで比較する。

## 2. 性能マトリクス

各条件を一定回数繰り返し、JVMウォームアップを経て測定する。JITの影響を区別するため、コールド起動も別に記録する。

| 変数 | 条件例 | 見たいこと |
| --- | --- | --- |
| ID数 | 1万・10万・100万（必要なら100万以上） | 人口増と計算量の比例関係 |
| 共通計算率 | 高/中/低（同一Stateが多数/少数） | 集団共有の利益と最悪条件 |
| 分岐頻度 | 曲がり角の少ない/多い道路 | 次境界のイベント数と索引コスト |
| 同時刻の集中 | 信号1基で一斉待機/再開 | 大量IDの部分許可・ヒープ/GC |
| 条件変更 | 道路閉鎖0/少/多、速度改善/悪化 | 予約失効・再計算のコスト |
| 可視個体 | 0/数百/数千、カメラ移動回数 | 詳細計算と表示の分離 |
| 都市の形 | 一本道/格子/密接ネットワーク | 経路探索と交通混雑の負荷 |
| 保存 | セーブなし/一定間隔でスナップショット | 一貫性維持と保存時停止 |

**比較対象:** 同じ世界・seed・ルール・時刻精度で、(A) 全IDの定期更新、(B) 集団の最早到着イベント方式、(C) 必要に応じて区間全体の一括予測方式を比較する。違うルールの結果を速度だけで比較しない。

### 必須計測項目

- 単位ゲーム時間あたりのCPU時間・wall time、イベント処理件数、待機解除・失効再予約件数、集団数と分割頻度。
- heap使用量とオブジェクト割当量、GC回数・累計停止時間・長い停止の分布。
- 1イベントの処理時間のp50/p95/p99、進入要求の遅延、時間進行速度の安定度。
- 描画FPS（可視化がある場合）とシミュレーション更新時間を別計測。
- バッチ化によるイベント削減率、集団内の最早到達キュー管理コスト、低共有率で悪化する条件。

## 3. 性能を理由に正しさを下げない

- まずC01〜C14を通す。合格前の高速化は仮説に留める。
- 「遠方なので必要な境界イベントを飛ばす」「カメラを向けると初めて事故や渋滞が発生する」は合格にしない。
- 性能が不十分なら、**イベントキュー・集団キー・到着時刻の持ち方・通知範囲**を個別に計測し、改善を比較する。
- 特定の地域や交通混雑で分岐が爆発する場合の退避方式は、保存則/遅延精度を定義してから追加する。
- 数値目標（例: 必要な最大人口、メモリ上限、FPSなど）はプレイ要件と対象ハードウェアを定めてから記録する。「Citiesより軽い」を未検証のまま完了条件にしない。
