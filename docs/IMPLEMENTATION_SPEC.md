> 詳細な実行意味論は [ランタイム実行契約](RUNTIME_PROTOCOL.md)、交差点の挙動は [交通の縦断仕様](TRAFFIC_VERTICAL_SLICE.md)、都市分野の更新は [都市システム統合仕様](DOMAIN_INTEGRATION.md)、合格基準は [検証計画](VALIDATION_PLAN.md) にまとめる。本書は全分野で共有する**上位契約**とし、同じ内容を重複規定しない。

## 1. 設計目標と禁止する短絡

- **個体の同一性と計算の実行を切り離す。** 人・車・建物などは必要に応じて安定したIDを持つ。個体数とオブジェクト数の比率を目的にはしない。
- **共通計算を共有し、境界で分岐させる。** 同じルールを持つIDの集団へ計算結果を適用し、到達・分岐・容量競合・条件変化でだけ必要な集合を分割する。
- **時間的LODはイベントを飛ばさない。** 画面外の区間を5秒先まで予測することはできるが、途中3秒で重要な変化が起きたらその時点を処理する。
- **論理シミュレーションと表示の詳細度を分ける。** 描画範囲だけ局所的な詳細位置・物理・見た目を計算する。画面外の渋滞・供給停止・信号・交通容量等の結果は維持する。
- **大量IDをすべて毎フレーム走査しない。** 全件走査が必要な業務（例: 一括初期化/ロード/統計構築）は頻度と理由を明示する。
- **OOP/UPDの規約はhot pathを含め適用する。** 役割を最小の抽象契約とfinal実装に分離し、プリミティブ配列などの内部表現はカプセル化する。具象クラス継承・オーバーロードは禁止。

## 2. UPDと責務境界

| 層 | 責務 | 他層への契約 |
| --- | --- | --- |
| UI | カメラ、建設操作、表示データ/アニメーション、可視対象の補間 | `CityCommand`等をProcessへ入力。Processの読み取り用`CityView`を描画。Dataへ直接接続しない |
| Process | 建設・課税・人口・経済・移動・State・イベント・交通容量・施設運用の**ゲーム結果の確定** | コマンドを検証し`CommandOutcome`を返す。必要時にData契約へ保存要求を出す |
| Data | マップ・設定・セーブの取得と保存、形式検証、I/Oエラーの検出 | シリアライズされた値と読み書き結果のみProcessへ返す。ゲームルール判断を行わない |

UIが可視対象を伝えることは許されるが、**可視化だけで通行の許可・需要量・税収等の論理結果を変更しない**。ゲーム結果に影響する個別衝突の判断はProcess側、描画だけの補間はUI側。

## 3. 共通モデル（型名はv0.1の設計上の契約名）

| 概念 | 必須情報・所有者 | 不変条件 |
| --- | --- | --- |
| `EntityId` | 長期安定のID、Processに一意な管理。人・車・建物等の型と合わせて識別 | 生成・消滅の明示イベント以外で欠落・重複しない |
| `GroupKey` | 対象種、State、区間/設備、処理ルール、境界、必要な時刻帯など | 同じルールと補正を安全に共有できるIDだけをまとめる |
| `GroupMembers` | ID集合＋必要に応じた個別進路/開始時刻/補正量、Process所有 | 単なる人数へ圧縮してID別の到達・分岐情報を失わない |
| `NetworkSegment` | 区間ID・接続ノード・長さ・種類・容量・制限・改訂番号 | 接続不能な区間間へ無断移動しない |
| `Boundary` | 入口/出口・適用State・進入条件・容量/優先度・改訂番号 | 条件を満たさない移動は受理しない |
| `MovementPrediction` | 区間内の共有ルール、開始時刻、到達予定時刻、参照した版番号 | 予測条件が変更されたら再計算・無効化できる |
| `MoveRequest` | 対象IDまたはID集合、元区間、先区間、要求時刻、進路 | ID/容量を無視した一括承認をしない |
| `MoveDecision` | 許可ID、待機ID、State切替対象、理由、次回起動条件 | 部分許可を表現し、許可/待機IDの集合が元の要求と一致する |
| `ScheduledEvent` | 時刻、種別、対象ID/Group/設備、参照版、安定した並び順 | 旧版イベントが確定状態を上書きしない |
| `CityView` | ProcessからUIへ渡す読み取り専用のスナップショット/差分 | 内部可変状態やDataのハンドルをUIへ公開しない |

初期の識別子は**64bit整数**を基本候補とし、型安全なAPIと大量IDの内部表現を分ける。ゲーム世界の同一性は`Citizen`のような具象クラスの存在数に依存させない。

**v0.2の追加契約:** 正規の個体StateはProcessが一元管理し、集団所属は派生索引、描画状態は読み取り投影とする。集団が共有するのは移動規則であり、IDごとの到達時刻まで一律にする必要はない。最も早い到着バッチだけをイベント予約して順に次のStateへ移す（詳細は[RUNTIME_PROTOCOL](RUNTIME_PROTOCOL.md)）。

## 4. 処理の契約と結果分類

```text
UI: PlaceRoad / ZoneParcel / SetBudget などのCityCommand
           ↓
Process: CommandValidator → 該当ドメインの担当
           ↓
Process: WorldStateを更新 → 必要な変更イベントを予約/発行
           ↓
Process: CityView/CommandOutcomeを構築 → UI
           ↘
            Data: セーブ等の取得・保存（必要時だけ）
```

移動の場合:

```text
GroupMembers + GroupKey + 現時刻
    → 移動予測 (MovementPredictor)
    → 到達予定イベント (EventScheduler)
    → 境界へ到達 (BoundaryResolver)
    → MoveDecision
          ├─ Allowed: 許可されたIDが次区間へ
          ├─ Transition: Stateが不一致なので指定Stateに切替
          ├─ Wait: 信号・歩行者・容量などの解除条件まで待機
          └─ Invalid: 誤ったID/区間/経路として拒否（ゲーム異常と区別）
    → GroupMembershipが必要なIDだけ分割・合流
```

- State不一致による再振り分けは**通常の制御フロー**であり、予期しない例外ではない。
- 進路が同じでも**到着予定時刻の異なるIDを一括で到着済みにしない**。到着予定時刻・順序・容量に応じた部分集合で解決する。
- 複数グループの同時進入は、境界単位で容量予約/優先順位を調停し、結果を**原子的**に確定する。
- 通過許可・State遷移でIDを消去・複製しない。集団の分割・統合はID集合の保存を検査する。
- 待機は解除イベント（例: 信号青、空容量発生、列車到着）へ登録し、毎フレーム再ポーリングしない。

## 5. 時間・イベント・予測失効

1. シミュレーション時刻の初期表現は`Long`型の**ミリ秒単位整数**とする。ゲーム日付/時刻の変換は別責務。
2. キューの初期実装は優先度付きイベントキュー。処理順は`(scheduledAt, microRound, phase, stableSequence)`で決定し、同一条件・同一seedでの再現性を検証する。
3. `phase`は同時刻の**退出と容量解放→信号/条件変更→進入判定→集計通知**などの依存順序を表す。先行phaseへ戻る新イベントは同時刻の次`microRound`で処理し、ゼロ時刻ループを監視する。初期の位相案は[RUNTIME_PROTOCOL](RUNTIME_PROTOCOL.md)を参照。
4. 予測が依存した道路・信号・容量・天候・政策等の改訂番号を保持する。変更時は影響範囲の予約を無効化し、**変更時刻の位置で再アンカー**して対象を再予測する。到着が以前より早くなるケースも遅くなるケースも即時再予約する。
5. 短時間のイベントが同一時刻で無限循環しないよう、1イベント処理時の状態進行・再予約条件を保証する。違反はテストで検出する。
6. 最初は**論理状態の確定を単一の決定的処理系列**として実装し、並列化は計算前処理や相互に独立な単位に限定する。必要性は計測で再判断する。
7. 固定の「遠方5秒」更新は**性能の選択肢**であって、境界の通過時刻を5秒刻みに丸める契約ではない。イベントを最優先する。

## 6. 都市機能を同じエンジンへ接続する規則

| 分野 | 共通計算の単位例 | 状態変化の起点例 | ID/集計上の保存対象 |
| --- | --- | --- | --- |
| 地形・区画 | 敷地・影響区域、建築条件のキャッシュ | 地形/道路変更、再区画 | 土地ID・建物IDと占有・敷地重複 |
| 住民・建物 | 世帯/行動条件/建物用途/地区 | 入居・退去・就業・時間帯切替 | ID同一性、世帯・建物の定員 |
| 道路・歩行者 | 区間+State+行先の共有移動モデル | 区間到達・信号変更・容量解放 | 進入台数、人の行先・到着 |
| 公共交通 | 路線便・駅/停留所・乗車待機群 | 便の到着/出発、乗降、満員 | 乗客ID、編成定員、運行時刻 |
| 産業・物流 | 商品/産業/地区の生産バッチ | 生産完了・納品・欠品 | 原材料・在庫・生産量の収支 |
| 電力・水・ごみ | 配送・供給網の区域/接続成分 | 需要増減・設備停止・容量不足 | 供給・需要・設備容量 |
| 公共サービス | 対象地区/施設/待機群 | 発病・通報・入学・出動・診療完了 | 施設定員・対応中ID |
| 環境・災害 | 空間グリッド/地区の集計場 | 排出・天候・災害・復旧 | 汚染・被害の収支と影響範囲 |
| 財政・政策 | 期間・地区・課税種別 | 日次/週次等の会計締め、税率変更 | 現金残高、収支の二重計上 |
| UI・保存 | 読み取り用投影・スナップショット | コマンド・時間操作・ロード要求 | 保存版・ID・イベント整合 |

**原則:** 数量（電力・税・汚染・在庫等）は必ずしも個体IDを必要としない。一方、通行・乗車・所属など個人の同一性に意味があるものはIDを維持する。

### 分野別のIssue

各Featureの**保存する状態/共有計算・トリガー/State遷移・依存・最小検証シナリオ**は対象のIssue #13〜#60に記載する。分野別の親Issueは #4〜#12。個々の機能ルールはIssue側を正本とし、この文書は共通の契約を規定する。

## 7. 実装上のユニットと公開APIの考え方

公開APIは役割ごとに小さな`interface`、具象実装は`final`。一例:

- `IdRegistry` : IDの生成/存在確認/明示的消滅
- `GroupMembership` : 共有可能なID集合の構築・分割・統合
- `MovementPredictor` : 区間内の到達時刻を予測
- `BoundaryResolver` : 移動リクエストから進入許可/待機/State切替を判断
- `EventScheduler` : イベント予約・失効・実行順序
- `RoutePlanner` : 経路探索・再探索の条件
- `NetworkIndex` : 区間・接続・影響範囲の管理
- `CapacityLedger` : 定員/容量の一貫した予約・解放
- `WorldProjector` : UIへ読み取り用情報を作成
- `WorldRepository` : Data境界での保存/復元

上記は**責務の候補名であり、1個体ごとに実装インスタンスを生成する指示ではない**。クラス名のためだけの抽象化は禁止。共有計算を成立させる最小の役割だけを採用する。

- 具象継承禁止（抽象クラス/インターフェースのみ）、オーバーロード禁止、具象`final`、移譲、1クラス1責務、1関数1処理、制御ネスト2段以内、カプセル化必須。
- コア内部は必要に応じてプリミティブ配列・コンパクトな構造を使う。管理オブジェクトの内部状態はUIや他の処理に直接公開しない。

## 8. 横断歩道の実装基準シナリオ

1. `SidewalkWalking` の集団が交差点境界へ到達。次区間が横断歩道なので`MoveRequest`を出す。
2. `BoundaryResolver`が現在Stateに不適合と判定。`CrosswalkWaiting`へIDを再振り分け。
3. 横断開始時に青なら容量に応じてIDを`CrosswalkWalking`へ移す。赤なら`SignalGreen(crosswalkId)`へ購読し休止。
4. 青になれば購読中集団へ通知。道路占有と優先関係で入場可能なIDだけ進入。残りは待機。
5. 横断途中の通常の赤信号では戻らず、終端到達で次の歩道へ`MoveRequest`。`SidewalkWalking`へ戻す。
6. 同じ時刻に車両の進入要求がある場合は横断歩道の容量・優先を一元的に解決し二重進入しない。
7. UIは近距離のIDだけ補間/必要な詳細表現を行う。カメラの有無は通行許可と到達時刻を変えない。

## 9. 共通テスト・ベンチマーク契約

### 正しさ（必須）
- 全IDが一意、集団分割・統合前後の集合が保存される。
- 容量・在庫・資金・人口等の保存則/整合性を機能別テストで確認する。
- 予約失効・同時刻イベント・状態遷移・信号待ち・部分許可が再現可能。
- カメラの位置/描画FPSにより**ゲーム結果**（人口・交通量・資金）が変わらない。
- セーブ→ロード→再実行で同じ入力/seedの論理イベント系列が一致する。

### 性能（実測する）
- 1万・10万・100万ID、共有率・分岐率・可視数を変え、CPU時間/GC/メモリ/イベント/集団数/1秒あたりの処理回数を記録。
- 全IDを逐次更新するベースラインと比較する。ただし性能改善の程度は未測定として扱う。
- 「都市規模拡大で重くならない」は目標。地形グリッド、経路探索、描画、都市の複雑性は別に計測する。
