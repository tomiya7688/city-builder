# ランタイム実行契約 v0.2 — ID集団・時間・イベント・整合性

> **設計仕様（未実装・未計測）**。共通モデルは [IMPLEMENTATION_SPEC.md](IMPLEMENTATION_SPEC.md)、思想は [SIMULATION_DESIGN.md](SIMULATION_DESIGN.md)、OOP/UPDの必須規約は [CODING_RULES.md](CODING_RULES.md) を参照。この文書は特に Phase 0 の**動作意味**を定める。性能を断定しない。

## 1. 一つの正しい状態と派生インデックス

Processが管理する `WorldState` の各 `EntityId` に対して、**同時刻に有効な論理位置・移動State・現在の所有区間・予定行動は一意**とする。データ格納が個別オブジェクトか配列かは無関係。

- `EntityStateStore`（役割名）はIDの現在State、所有区間、移動開始時刻、経路上の次境界、所属世帯/車両等の**正規状態**を保持する。
- `GroupMembership` は「同じ計算を適用可能なID集合」の**派生索引**。集団の分割・統合とState確定を一つの処理境界で行う。索引だけ更新して正規状態を置き去りにしない。
- `RenderProxy`/可視リストは**読み取り専用の投影**。画面外に出てもEntityIdや論理位置が消えない。UIは移動許可や交通量を確定しない。
- `EntityId` はセーブ内で再利用しない64bit整数を初期候補とする（新規IDが必要な場合のみ採番）。グループID・予約IDは別の識別子として扱い、ID番号からゲーム内位置や種類を推定しない。

`State` は何でも一つの巨大な列挙へ詰め込まず、**処理の種類（歩行/横断/乗車/待機等）**と**待機理由・区間・次の境界・進路**を必要に応じて分離する。Stateの種類を増やさずに異なる交差点や駅を扱えることを目指す。

### 不変条件

1. 生存中のIDは論理的な移動所有者（区間/施設/世界内待機先）をちょうど一つ持つ。乗客IDと車両IDは別の実体でも、乗客の移動所属は同時に複数の車両へ割当しない。
2. グループはIDの**重複を持たない分割集合**。分割・合流後のID集合は前と一致する。生成・死亡・域外移管は独立したイベントとして扱う。
3. `EntityStateStore` と `GroupMembership` は確定イベントの終了点で常に一致する。表示用キャッシュは正規状態にならない。
4. 予約は、対象ID/集団がまだ存在し、保持した版が有効である場合だけ状態を変更できる。

## 2. 集団共有移動と「次の到着者」

一集団の共有条件を `(EntityKind, State, SegmentId, TravelRuleVersion, ExitBoundaryId, Direction)` などで定義する。**同じ計算法を使用することは、同時に到着することを意味しない**。

一人の区間上の論理進捗は初期段階では線形モデルとする:

```text
p_i(t) = clamp((t - enteredAt_i) / travelDuration_i, 0, 1)
position_i(t) = segmentGeometry(p_i(t))
arrivalAt_i = enteredAt_i + travelDuration_i
```

- `travelDuration_i` は共通の区間条件から計算し、必要な差分（速度区分・出発時刻等）のみIDに保持してよい。
- 速度/出発時刻/出口が同じならまとまった到着バッチにする。異なる場合も区間内計算は共有可能だが、**到着順は正しく維持**する。
- グループ内の到着候補を `(arrivalAt, entityId)` 順に並べ、原則**最も早い到着バッチのイベントだけ**グローバルキューへ予約する。到着処理で対象IDを取り除き、次の最早バッチを予約する。個体全員に毎フレームイベントを発行しない。
- 集団内インデックスの方式（時刻バケット、ソート列、局所heap、共通時刻＋差分）はベンチマークで選ぶ。個人ごとの独立した出発条件が増えるほど計算共有率が下がることは許容し、**見かけのO(1)を主張しない**。
- 一人ずつ異なるタイミングで分岐する最悪条件では多数のイベントが必要になる。これは同一性を失わない設計上の必要コストであり、検証対象とする。

同じ計算を複数集団で共有する場合は、**関数・不変の係数テーブル・安全なキャッシュ**を共有する。共有結果を使ったID別の状態確定までは共通化したことにならない。

## 3. 論理時刻と同時刻イベント

時刻は `Long` ミリ秒。イベントの完全な安定順序キーを初期案として以下とする。

```text
(scheduledAt, microRound, phase, stableSequence)
```

`phase` の意味:

| phase | 目的 |
| --- | --- |
| 0 | 外部コマンド/構造変更など、現在時刻の入力確定 |
| 10 | 移動完了・退出・施設利用完了・占有の解放 |
| 20 | 信号/インフラ/ポリシー等の条件変更、待機解除通知 |
| 30 | 境界への進入判定・State遷移・容量確保 |
| 40 | 確定差分からの統計・通知・読み取り用投影作成 |

- **同時刻・同一ラウンドの位相を逆行してはいけない。** phase 30で新たなphase 20の処理が必要なら `microRound+1` に予約する。
- 同じIDが同じ時刻に無限にStateを行き来するループは許さない。ラウンド/遷移回数の安全上限と原因情報を設け、違反はテスト失敗にする。上限値は実装時に決める。
- `stableSequence` はProcessが決定的に採番し、並列実行順で揺らさない。外部コマンドの順番も論理時刻の境界で確定する。
- UIの描画頻度やワーカーの終了順では`scheduledAt`も`stableSequence`も変えない。並列化はまず純粋計算に限定し、状態確定の順序を固定する。

例: 青信号への変更が t=7.000s、歩行者の進入要求も t=7.000s の場合、位相20で青を確定し、位相30で青を参照して進入判定する。赤への変更でも同じルールで進入を停止する。

## 4. MoveRequestの原子的確定

`MoveRequest` は要求ID/ID集合、元区間、先区間、境界、要求時刻、元State、期待した所有版を持つ。

`MoveDecision` は対象IDを重複なく **Allowed / Transition / Wait / Invalid** へ割り当てる。部分許可を認め、**結果のID集合の和＝要求ID集合**を保つ。

1. Processが対象ID・所有区間・現在State・進路を検証する。
2. 必要なStateの切替（例: SidewalkWalking→CrosswalkWaiting）を返す。
3. 進入ゲートは信号・優先関係・競合領域・区間容量・待ち順を判定する。
4. 容量を一つの `CapacityLedger`（責務名）で**予約→確定**する。複数要求は同時に容量を取れない。
5. 許可分だけ区間所属と占有・予約を移し、残りは理由付き待機群へ所属させる。
6. 待機を引き起こした条件に `WaitKey = (BoundaryId, Reason, ConditionVersion)` 等で購読し、変化時のみ再試行する。待機条件が既に成立しているなら同時刻の次ラウンドで即再試行できる。

`CapacityLedger` は区間内占有数・境界の同時通過許可数・競合領域の予約数を**異なる概念**として持つ。信号が青でも占有・優先条件で全員通れるとは限らない。公平性の最初の候補は「優先条件→到着時刻→安定したID/sequence」であり、緊急車両など例外は明示ルールで導入する。

**クロスウォークの占有が0に戻った事実**は、車の `WaitingForPedestrian` 群の再開条件になれる。歩行者が青になるだけで車を通してはいけない。

## 5. 予測の失効は「遅延だけでなく早着」を防ぐ

例: 遠方の車を12秒後に交差点へ到達するよう予約した後、途中で道路が空いて8秒後に到達するようになったとする。**古い12秒イベントが実行されるまで無視するだけでは4秒遅れる。**

- 予測は区間/信号/速度/経路の参照版を記録する。
- 変更時に `SegmentId→影響GroupId` 等の逆引きから対象集団を探し、変更時刻で進捗を再アンカーし、新しい到達イベントを予約する。旧イベントは失効させる。
- 再アンカーは**変更前の移動規則を変更時刻まで積分/評価した位置**を基準とし、瞬間移動を起こさない。
- 変更後の新しい到達が**古い到達より早い場合も遅い場合も**、正しい次イベントを予約する。
- 影響索引が巨大になる場合、区間や集団の単位で段階的失効/再計算する。結果を遅延させる場合は、時刻整合が守れる上限・条件を明示して検証する。

例外的な瞬間閉鎖や災害では、通行途中のIDをどう扱うか（停止・退避・進路変更）をゲームルールとして定義し、描画の都合に委ねない。

### 失効イベントの蓄積を防ぐ

版番号だけで旧予約を無視する方式では、長く残った旧イベントが優先度キューに蓄積する可能性がある。予約には取消トークンを持たせ、実装候補として**明示的取消・一定割合での決定的な再構築・有効予約だけの再挿入**を測定する。キューの実要素数・有効件数・失効率と再構築コストをベンチマークに含める。再構築後もイベントの安定順序と次の最早到達時刻が変わらないことをテストする。

## 6. 描画範囲の変更と個別物理

- 正規の移動・信号・渋滞・容量判断は**Processの論理計算**であり、可視性で変えない。
- 可視範囲での歩き方、車間表現、微妙な避け動作など**都市の状態を変更しない部分**はUI側で補間できる。
- 事故・進入可否・実際の到着時間を変える物理相互作用はProcessの責務。画面内だけ詳細演算を使う場合でも、画面外との意味論上の差が都市結果を変えないことを別途検証する。初期Phaseでは**非権威的な表示補正に限定**する。
- カメラ移動時、ID・区間・進捗・State・描画スナップショット時刻から表示を再構築する。可視化されなかった間のState遷移を「描画のために後追い実行」しない。
- 表示対象が多すぎるときは表示密度/アニメーションを下げても、論理的な人数を失わない。

## 7. 永続化・乱数・再現性

- セーブ境界は**同時刻のイベント確定ラウンドの完了点**とする。Processが読み取り可能な一貫したスナップショットを作り、Dataは書式変換と保存だけを行う。
- スナップショットはID生成カウンタ、正規State、所属、区間/条件版、容量予約、待機購読、論理時刻、イベントキュー、安定sequence、乱数seed/必要な乱数状態を含める。
- ロード時はProcessが参照整合性とID集合を検査し、派生索引を再構築/検証する。途中失敗で現行都市を壊さない。
- 非決定的な並列実行・システム時計・HashMapの不安定順序をゲーム結果の決定へ持ち込まない。個体差の疑似乱数は `(worldSeed, EntityId, purpose, occurrence)` 等の安定キーから求められる方式を優先する。

## 8. Phase0の検証ゲート

1. 同じ集団の3人がそれぞれ5/6/7秒で到着する場合、到着を一括確定せず順に処理する。
2. 1000IDの要求を容量100に対して処理し、100許可/900待機、占有解放後の再開でもID集合が保存される。
3. 同時刻の青/赤への変化、退出、再進入、競合車両で再現可能な結果を得る。
4. 条件変化で到達が早まる/遅くなる両ケースを検証し、旧予約で誤って状態変更しない。
5. 同じ入力/seedで可視範囲を動かす/動かさない両実行の**正規世界状態のハッシュ**が一致する。
6. セーブ→ロード→再開で、時刻・State・ID集合・残予約・同時刻処理順が一致する。
7. 1万/10万/100万IDに対し、共有率・分岐率・ネットワーク変化頻度も変え、逐次更新方式との計測結果を記録する。
