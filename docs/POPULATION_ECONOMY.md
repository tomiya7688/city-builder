# 住民・世帯・経済・物流・都市財政仕様 v1.0

> ゲームルールの正本。時間・State・IDの確定順は [RUNTIME_PROTOCOL](RUNTIME_PROTOCOL.md)、共通計算と量の保存則は [DOMAIN_INTEGRATION](DOMAIN_INTEGRATION.md) を優先する。数値は初期バランスであり、完成前にゲームプレイで調整する。

## 1. 住民は「個体の同一性」と「共有する生活モデル」を両立させる

住民は \`CitizenId\`、世帯は \`HouseholdId\` で追跡できる。IDが100万人分あっても100万人が毎フレーム意思決定するわけではない。

| 情報 | 個体または世帯に保持するもの | 共通計算できるもの |
| --- | --- | --- |
| 人口統計 | ID、出生年/年齢層、世帯、居住地区 | 年齢層ごとの出生/死亡/移住率 |
| 生活 | 自宅、就業先/学校、状態、次の予定と時刻 | 平日/休日、年齢/仕事別のスケジュール |
| 交通 | 現在の移動区間、経路、到達予約、待機理由 | 同条件の移動速度/所要時間/交通手段選択 |
| 経済 | 世帯の所得階級・購入需要、職業/教育 | 所得帯・地区別の消費率と購買量 |
| 健康・教育 | 就学・治療・卒業等の現在State | 年齢・地域・サービス水準に基づく発生率 |

**住民の「所在」「住所」「勤務先/学校」「移動目的」は別属性。** 自宅の登録先を通勤中に書き換えない。個体IDの存在を省略して人数だけにしてしまう設計は避けるが、個体オブジェクトの生成数は固定しない。

### 住民ライフサイクル

- 新生児の出生で新しいCitizenIdを払い出し、世帯へ所属させる。既存IDを再利用しない。
- 加齢、就学、就職、転職、失業、引越、病気、回復、退職、死亡、転出を時刻イベントや条件変化で処理する。
- 初期年齢区分は0〜5、6〜17、18〜24、25〜64、65歳以上。就労/在学/年金/教育のルールと接続する。年齢は日付との差分で導出し、個体ごとの毎フレーム更新はしない。
- 死亡/転出で現在予約された通勤・乗車・診療・勤務先予約を解除し、関係施設の定員・税基礎へ差分を反映。
- 個人の表示名・外見・一部の嗜好はseedとIDから決定的に導出してよい。転職/転居/病歴など変化する事実は保存する。

### 世帯と住居

世帯は1〜5人を主な初期分布とし、単身・共働き・子育て・高齢世帯を持つ。住宅の容量は**居住可能な世帯/住戸単位**で判定し、人口は実際に入居した世帯の人数から数える。子が生まれたとき人口が増えても住戸が自動増殖しない。

入居は `HousingRequested → ResidenceReserved → MovedIn`。住宅が満杯なら待機/他の住宅へ。住戸予約は原子的に処理し、同じ世帯が複数の住居に居住したことにしない。

## 2. 市民の1日の過ごし方

曜日・職業・年齢・在宅勤務・施設営業時間を組み合わせた**スケジュールテンプレート**を共有する。

例：平日の労働者は `AtHome → Commuting → AtWork → ReturningHome → AtHome`。学校児童は `AtHome → GoingToSchool → AtSchool → ReturningHome`。買物は世帯所得・商業アクセス・週次需要から生成する。

- 活動の開始はゲーム暦で予定しSimClockへ変換して登録。通勤は道路・歩道・公共交通の実際の所要時間で到着時刻が決まる。
- 予定時刻/移動時間が違えば同じ生活テンプレートでもIDが別々に分岐する。次回の境界到着順を維持する。
- 施設が閉鎖された場合、予約済の目的地・買物・勤務の対象群を再計画。既に移動中のIDは所在/経路の連続性を維持する。
- 通勤の失敗は交通負荷、遅刻、労働生産性、幸福度などへ控えめに影響する。赤信号1回の待ちで即退職するような極端な連鎖を避ける。

### 就業・教育・失業

- 建物は職種別の雇用枠と必要な教育水準を持つ。住民が転入/卒業/転職または企業が拡張したときに空席マッチングを起動する。
- 就業マッチングは教育の適合、賃金帯、通勤総費用、勤務地の定員で評価する。完全最適割当は要求せず、地域別候補探索と固定seedでの選定を使用。
- 仕事なし・学校なしは明示State/統計として保持。失業は税収や転出へ遅延して影響し、急激な市民消滅を起こさない。
- 学校は年齢と定員で就学を判定し、在学期間後に教育水準を更新。高等教育はオフィス/高度産業の雇用適性へ作用する。

## 3. 用途需要の計算

建設の需要は**不足している収容能力**と**都市の魅力**を分けて求める。表向きは住宅/商業/工業/オフィスの4種類の需要バー（0〜100）を表示。

| 用途 | 内部的に計算する不足 |
| --- | --- |
| Residential | 都市へ流入希望/新世帯化する世帯数 − 空き住戸数 |
| Commercial | 住民/観光客の購買需要が支える商業床面積・店舗枠 − 既存有効供給 |
| Industrial | 原料/商品への需要・輸出可能量が支える工業生産/雇用枠 − 既存有効供給 |
| Office | 教育人材・サービス需要が支えるオフィス就業枠 − 既存有効供給 |

各不足を都市の規模・上限と平滑化で正規化してバーへ変換する。全都市単一の魔法の値にせず、地区/用途ごとの需要を持ち、都市総需要は合計/重み付き表示。

`Demand = clamp(Normalize(Shortage) × AttractivenessModifier × AffordabilityModifier, 0, 100)` を初期形とする。係数は `GAME_BALANCE_RELEASE` の設定で調整する。バー表示だけではなく**「空き住戸が多い」「求人不足」「商店不足」など内訳の理由**を見られるようにする。

需要を一度評価した後、人口・施設容量・公共交通・税・汚染の条件が変わった地区だけ再評価する。表示スムージングはUIだけで行い、論理的な不足を隠さない。

## 4. 住宅・商業・工業・オフィスと供給網

- **住宅:** 入居率、世帯数、レベル、地価、サービスとアクセスに応じて税収が生じる。
- **商業:** 食料、日用品、娯楽等のサービスを販売。商圏、購買力、在庫、従業員、輸送から売上が決まる。
- **工業/農林鉱:** 資源と労働力を使って製品を生み、倉庫/店/外部へ輸送。原料不足や輸送遅延で生産速度が下がる。
- **オフィス:** 教育水準・通信/電力・アクセスに依存した仕事と税基礎を生み、日用品などの物理貨物需要は工業より小さい。
- **観光・娯楽:** ランドマーク/公園/交通から市外客需要を生成し、商業の売上・混雑へ反映。

### 商品カテゴリ

v1は**食料、日用品、建材、燃料、工業素材**の5商品カテゴリを初期標準とする。企業ごとの貨物は `ProductionBatchId / ShipmentId / InventoryLedger` で管理する。工場1つにつき商品アイテム1個を人間と同じ物理計算で動かさない。

`原料予約 → 生産イベント → 倉庫在庫 → 貨物輸送イベント → 店舗/工事で消費`。数量は整数単位と必要な端数を扱う。輸送中の同じ荷物を別倉庫の在庫として二重計上しない。

外部からの輸入/輸出はマップのExternalPortを通じる。外部経済は価格/輸送容量/需要の集約パラメータとして扱い、マップ外の国全体を個別シミュレーションしない。

## 5. 所得・財政・予算の仕組み

City Treasuryは単一の残高と**二重計上を防ぐ取引元帳**を持ち、Creditの1/100を整数最小単位として記帳する。

### 収入と支出

| 収入 | 支出 |
| --- | --- |
| 住宅からの固定資産/住民所得相当税 | 道路・橋・施設・造成の建設費 |
| 商業/工業/オフィスからの事業税 | 電力・浄水・下水・ごみ処理の運営費 |
| 公共交通の運賃・施設利用収入 | 医療・教育・警察・消防・公園の維持費 |
| 市域拡張に伴う補助金（限定） | 借入金の利息・元本返済 |
| 域外流通/観光の税・利用収入 | 緊急災害対応・修復費 |

**日次の会計締め**で税基礎、サービス運営費、利息等を一度だけ確定する。工事・ローン実行など即時支出は承認時点の一意なTransactionIdで記帳する。倍速やセーブ再開後も同じ期間の税収を二度足さない。

税率の初期値（調整可能）: 住宅9%、商業10%、工業10%、オフィス10%。UIは各税率による需要/転入/収支の予測と過去推移を表示。税率を過度に上げると建設需要・転入・企業利益に遅れて悪影響が出る。ゼロ税でもサービスの無料稼働を無条件に保証しない。

公共サービス予算は部門ごとに50〜150%の範囲で調整（初期100%）。予算が低いと車両出動数、施設定員/処理能力、サービス品質が段階的に低下する。建設費だけ払えば永久無料という設計にしない。

### 借入と財政難

- ローンは返済期間・残高・金利・上限を明示し、借入時にキャッシュフローを表示。
- 新規都市にも少額の緊急枠を与える。運用中は税収・信用の指標で貸出上限を更新する。具体金利と額はバランスデータで調整。
- 赤字なら建設費が足りない支出を拒否し、税調整・サービス予算削減・融資・資産撤去などの回復策を残す。
- サンドボックスは現金残高が危機的でも強制終了しない。シナリオでは明示した財政条件が一定期間続くと失敗にしてよい。

## 6. 地価・満足度・人口移動

各地区に `HappinessScore` と `LandValueScore` の0〜100の内部指標を持ち、個体や建物の差分が必要な場合のみ補正する。

### 満足度の初期構成

`Happiness = 0.20×住宅/負担余裕 + 0.20×雇用/所得 + 0.20×通勤アクセス + 0.25×公共サービス + 0.15×環境/安全`

各要素は0〜100に正規化し、地区と世帯属性の違いを補正する。係数は初期バランス案で固定し、プレイテストで調整可能とする。大きな一時イベントに直ちに全員転出で反応させず、**移動平均・閾値・継続日数**を使う。

地価はアクセス、雇用/商業、公共サービス、公園、汚染、騒音、地形/水辺、税負担を考慮する。上昇が良いだけでなく家賃・地価上昇により低所得住民の負担が増えるトレードオフを設ける。

### 人口変化

- 転入: 空き住戸、雇用適合、都市満足度、域外接続、税負担から転入希望世帯数を算出。受入先住戸予約成功後にのみCitizenIdを生成。
- 転出: 長期失業、住宅負担、公害、税、サービス不足で希望が増える。転出決定時に居住/仕事/移動予約を解除してExternalPortで市外移管。
- 出生・死亡: 年齢層・医療/環境条件をもとに地区/世帯グループ単位で発生数を決め、実際の対象CitizenIdだけStateを更新。
- 転居: 新しい住戸の容量確保を済ませてから旧住宅を解放。途中で住所が二重になることを防ぐ。

都市が一つの施策で即座に劇的な人口変化を起こさないよう、移住率・建物成長・税影響には最小待機日数と平滑化を使う。ゲームのバランス上はプレイヤーが数日〜数週間の遅延を理解できるUIを提供する。

## 7. 完了判定

- 住宅建設→転入→世帯/個人ID→就職→通勤→買い物→売上→税の一連の因果関係が成立する。
- 通勤先・現在位置・住居が別々に保たれ、就職・転居してもIDが変わらない。
- 住宅100住戸に101世帯の同時入居要求があれば、100のみ確定し1世帯は適切に待機/他施設へ回る。
- 生産・輸送・在庫・消費に数量の重複/消失がない。
- 税・維持費・ローンが停止/倍速/セーブ再開で二重計上しない。
- 汚染・公共サービス・道路改良などによる地価や満足度の変化原因をプレイヤーに示せる。
- 住民数が増えても、全員の生活判断を毎フレーム実行する必要がない。
