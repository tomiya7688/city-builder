# 開発・オブジェクト指向ルール

この文書は City Builder の **必須ルール**。設計・実装・レビュー・コード生成に適用する。変更する場合は、明示的な設計上の合意と本ドキュメントの更新を必要とする。

## 1. 基本方針

**強い責務分離を持つオブジェクト指向設計**を採用する。役割の明確な最小のクラスとメソッドを組み合わせ、継承による機能の使い回しより **移譲（delegation / composition）** を優先する。

シミュレーションの数値データをプリミティブ配列等でコンパクトに保持することと、処理をオブジェクト指向的に設計することは両立する。ID ごとに大量のクラスインスタンスを生成することは要求しない。

## 2. 必須の構文・設計ルール

### R1. 具象クラスを継承元にしない

- **継承・実装の契約として使ってよいのは抽象クラス（abstract class）またはインターフェース（interface）のみ**。
- **具象クラスからの継承を禁止**する。Java の `extends`、Kotlin の `:` 等も同じ意味で扱う。
- 継承は抽象契約を実現する用途に限定し、コードの再利用が目的なら移譲を使う。
- `Object` / `Any` 等の言語仕様による暗黙の基底型は対象外。
- フレームワークが具象クラス継承を強制する場合、勝手に例外扱いせず、アダプターや別技術の選定を先に検討する。

### R2. オーバーロード禁止

- 同じ名前を持ち、引数の数・型・順序だけが異なるメソッド／関数を定義しない。
- コンストラクタの多重定義や、Kotlin の `@JvmOverloads` による生成も避ける。
- 別の処理や入力形式なら、意図の分かる別名を付けるか、明示的な値オブジェクトを渡す。
- **オーバーライドは別概念**。抽象クラス／インターフェースの契約の実装は許可する。ただし R1・R3 を守る。
- 外部ライブラリが提供する既存のオーバーロードの「呼び出し」は禁止しない。自分たちの API をオーバーロードで設計しないというルール。

### R3. final の強制

- **すべての具象クラスを final にする**。Java は `final class`、Kotlin は原則 `final class` と明記する（Kotlin の既定値に任せず意図を表す）。
- Java の `record` / `enum`、Kotlin の `object` / `enum class` 等、言語仕様上拡張できず `final` を明示できない型は、そのまま許可する。
- 抽象クラスとインターフェースは final にできないため例外ではなく「継承の契約」として扱う。
- 具象メソッドはオーバーライド可能にしない。抽象契約を実装するメソッドはその契約に必要な宣言のみとし、そこからの再継承を前提にしない。

### R4. 継承より移譲を優先

- 機能を使い回すための基底クラスを増やさず、小さな役割のオブジェクトを組み合わせる。
- 例：移動の予測、進入可否の判定、State 遷移、イベント予約は別々の責務に置く。
- 型に応じた振る舞いは必要に応じてインターフェース契約へ移譲する。巨大な親クラスや多段階のクラス階層を作らない。

### R5. 1 クラス 1 責務

- 1 クラスに、一つの変更理由だけを持たせる。
- 例：`MovementPredictor` が描画とセーブ処理まで兼務してはいけない。
- データ保持用の型も、関係のない情報を詰め込む万能コンテナにしない。
- どの UPD 層に属するか説明できなければ分割を検討する。

### R6. 1 関数 1 処理

- 1 関数は **一つの説明可能な目的** を持つこと。複数の責務を連結しない。
- 「通行許可を判断する関数」がファイル保存や描画まで行ってはいけない。
- 手順の調整だけを行う関数は許容するが、個別の判断・計算・保存を自分で抱え込まず委譲する。
- 小ささそのものが目的ではない。名前と返り値、責務が明確でテストできることを基準とする。

### R7. ネストの制限

- 原則として **関数内の制御フローのネストを最大 2 段** とする。
- `if`、`when`/`switch`、ループ、`try`、条件分岐を含むラムダの内部を数える。クラス・関数の宣言括弧は数えない。
- 深くなる場合は早期 return、ガード節、移譲、処理の分割を使う。
- 人為的に小さな関数へ分けて責務を見失うことは避ける。具体的な静的検査を導入するときは数え方をテストで固定する。

### R8. カプセル化必須

- 内部の状態を外部が直接書き換えられないようにする。特に mutable collection、配列、State の所有権を明確にする。
- 原則 `private` なフィールドと、目的別の操作・読み取り API を使う。必要以上の public setter は作らない。
- ID、区間、時刻、遷移結果などは不変の値として受け渡すことを優先する。
- 異なる層へオブジェクトの内部実装や画面・保存ハンドルを公開しない。
- 大量 ID を持つ内部配列は境界を通して操作し、共有された可変配列を誰でも直接編集できる構造にしない。

## 3. UPD（UI / Process / Data）の厳守

City Builder は [UPD Design](https://github.com/tomiya7688/upd-design) に従う。これはフォルダ名の規則ではなく **仕事の責任範囲** の規則。

| 層 | 担当する | 禁止する |
| --- | --- | --- |
| UI | 入力、表示、描画、表示用補間、画面状態 | ゲームルールの最終判断、セーブ等の直接読み書き |
| Process | 都市シミュレーション、移動予測、State 遷移、進入判定、イベントスケジュール | UI の操作、ファイル／DB の直接読み書き |
| Data | セーブ／ロード、データ取得・保存、保存形式との変換、I/O 失敗の検出 | ゲームルールの判断、画面操作 |

要求の責務の流れは **UI → Process → Data**、結果は **Data → Process → UI**。実際には Data が不要な処理は Process で完結してよい。

- **UI ↔ Data の直接接続を禁止**する。イベントバス、共有ユーティリティ、中継オブジェクトを挟んでも禁止。
- Process が「保存すべきか」を判断し、Data が「どう保存したか」を返す。
- Data の読み書きエラーの意味付けは Process、画面での表現は UI。
- クラス名やパッケージ名を変えて責務をすり抜けることは禁止。
- UI では表現上の補間を許可する。ただし交通容量・衝突結果などゲーム状態に関わる判定は Process へ置く。

参照する正本：[UPD の必須境界](https://github.com/tomiya7688/upd-design/blob/main/docs/developers/boundaries.md)。

## 4. 設計例

**避ける設計**: `Citizen` という巨大な継承可能クラスが、移動、信号判定、描画、保存まで実行する。同名 `move(...)` を多数オーバーロードする。

**採用したい設計**（役割名は仮）:

~~~text
[UI]        CityRenderer            ← 可視 ID の描画と補間
             │
[Process]   MovementPredictor       ← 区間内の移動時間を計算
            BoundaryRequestResolver ← 境界への進入を解決
            StateTransitionResolver ← 新しい State を決める
            EventScheduler          ← 再評価時刻・条件を予約
            GroupMembership         ← 計算共有群と ID の所属を管理
             │
[Data]      WorldRepository         ← セーブとロード
~~~

各役割を小さなインターフェースと final 実装で構成し、協調動作は移譲で実現する。この構図は **責務の例** であり、実装前にクラスの数を固定するものではない。

### JVM 実装上の補足

- Java、Kotlin 等の採用と担当は今後の判断。UPD・責務・final の規則は言語が違っても守る。
- Kotlin の `data class` や `value class`、Java の `record`、プリミティブ配列は、カプセル化と責務分離を満たすなら利用してよい。
- `sealed` な型を使う場合も具象クラスを継承元にしない。継承元は interface / abstract class に限る。
- JVM の JIT に頼って無駄な個別更新が自動で集約されると期待しない。共有計算とイベント駆動は明示的に実装する。

## 5. レビューの合否基準

コードレビューでは最低限、次を確認する。

- [ ] 具象クラスの継承がない。継承元は abstract class / interface のみ。
- [ ] 自作 API の関数・コンストラクタにオーバーロードがない。
- [ ] final 指定（または final が暗黙で明示不可な型）を満たす。
- [ ] 継承での再利用ではなく移譲を使っている。
- [ ] 各クラス・各関数に一つの責務がある。
- [ ] 制御フローのネストが 2 段以内。
- [ ] 可変状態と内部データがカプセル化されている。
- [ ] UPD の全境界を、正常系と失敗系の両方で守っている。
- [ ] 描画範囲の変化が論理シミュレーションの矛盾を作らない。
- [ ] 大量 ID に対するオブジェクト割り当てや毎フレーム更新を無批判に増やしていない。

## 6. 自動検査と例外の扱い

- UPD は [up​d-design のチェッカー](https://github.com/tomiya7688/upd-design/tree/main/tools) を将来的に CI へ組み込む。現時点ではプロジェクトに検査対象コードがなく、検査・CI は **未導入**。
- 現在の UPD チェッカーは Kotlin の import 等の一部を検出するが、すべての責務違反を検出できるわけではない。Java を含む完全なチェックが導入済みとはみなさない。
- 継承・オーバーロード・final・ネスト等も、言語ごとに静的解析ルールを実装・検証するまではレビューで確認する。
- ルール違反を「性能のため」等の理由で黙認しない。衝突する要求があれば設計を見直し、必要なら先にルールの変更を議論する。
