# シミュレーション設計（初期仕様）

## 1. 目的と前提

本プロジェクトは Cities: Skylines に近い街づくり体験を目指す。ただし、個体数に応じてすべてを毎フレーム更新することは避け、**共通計算・個体 ID・State 遷移・イベント予約・時間的 LOD** を組み合わせる。

ここに記すのは実装開始前の設計方針。アルゴリズムや更新間隔は検証で調整する。

### 基本原則

1. **存在と計算は別**: 住民・車両の同一性は ID で保持するが、全個体に重いオブジェクトや連続更新を必要としない。
2. **人数だけに集約しない**: 「1,000 人いる」だけでは、誰が交差点へ到達し、どちらへ曲がるか分からない。集団内の ID と到達・分岐に必要な情報は失わない。
3. **共有できる計算は一度**: 同じ State・移動区間・移動規則を使う ID 群は共通の計算を利用する。個体差は小さなデータで表す。
4. **移動と通行判定を分離**: 区間内を進む計算と、境界への進入が認められるかというリクエスト判定を別の責務にする。
5. **判定は必要な瞬間に**: 曲がり角、横断歩道、十字路、歩道橋、駅などの境界、または待機条件の変化で State を遷移させる。
6. **可視範囲のみ詳細に**: 描画範囲内では細かな座標・見た目・局所計算を行う。画面外では主に論理的移動と予約イベントを処理する。
7. **距離に応じて時間間隔を伸ばす**: 遠方では数秒先の移動をまとめて計算できる。ただし途中のイベント・境界・容量制約は飛び越さない。

## 2. ID と集団のモデル

各個体は長期間安定する ID を持つ。ID と描画用オブジェクトを同一視しない。例えば住民 104 が画面外に出ても ID 104 は消えない。

| 保持する情報 | 用途 |
| --- | --- |
| Entity ID | 同一人物・同一車両の追跡 |
| 現在の State と区間 ID | 適用する移動規則と場所 |
| 次に判定する境界・進路 | 右折、直進、横断、駅への入場等 |
| 時刻・進行状態・必要な個体差 | 到達時刻や現在位置の復元 |
| 条件変化を反映する版番号等 | 予約の無効化・再計算 |

すべてを各 ID の独立したクラスに格納する必要はない。連続した整数 ID、プリミティブ配列、必要な部分だけの追加状態など、JVM に適したデータ表現を検討する。

### 集団の意味

集団は **「同じ処理を適用できる ID の集合」**。単なる人口カウンタではない。

- State、道路／歩道の区間、判定待ち対象、移動規則、必要なら時間帯・次の分岐先などでまとめる。
- 個別到達時刻が違っても、共通の移動規則と小さな差分を共有できれば同じ計算群に入れられる。
- 次の State や進路が異なれば、境界に到達した ID だけを別の集団へ移す。
- 再び同じ条件になれば集団を統合できる。
- 通勤・消費・施設利用などでは、同じ ID が計算分野ごとに異なる分類に属してよい。

「共有計算」は 1,000 ID の値の更新が必ず O(1) になる、という意味ではない。到達順や個体の同一性を扱う処理量、ID の転送量は必要に応じて発生する。

## 3. 移動モデルとリクエスト

### 基本の処理

~~~text
現在 State + 区間 + 移動条件 + 時刻
        ↓
区間内の移動を共有計算
        ↓
次の境界への到達を予約
        ↓
到達した ID または ID 集団の MoveRequest
        ↓
進入条件・容量・State 整合性を解決
        ├─ 許可: 次区間への移動を確定
        ├─ State 不一致: 次の適切な State へ遷移
        └─ 通行不可: 待機 State へ遷移し再開条件を登録
~~~

リクエストの「失敗」には種類がある。**状態に合わないため State を切り替える場合** と、**信号・人・容量等のため通行できない場合** を区別する。State 切り替えは予期された制御フローであり、システムエラーではない。

リクエストをまとめて処理しても、承認された ID と待機する ID を特定できる必要がある。道路や改札等の容量が足りない場合は部分許可を表現する。複数の要求が競合する場合は、処理順序・優先度・公平性を明示し、二重進入を防ぐ。

### State の例

| 区間・条件 | 主な State / 判定 |
| --- | --- |
| 歩道 | 歩行中、進路に応じて曲がり角を通過 |
| 横断歩道入口 | 横断待機（信号を確認） |
| 横断歩道内 | 横断中（通過中の信号を繰り返し判定しない） |
| 十字路 | 右左折・直進・横断等に応じた境界遷移 |
| 歩道橋 | 昇降・橋上移動へ遷移 |
| 駅 | 入場、改札待機、ホーム待機、乗車、降車 |
| 車道と横断歩道 | 走行、歩行者待ち、再発進 |
| 停留所・車庫等 | 停車、乗降、発車 |

すべてを固有の State クラスにしなくてもよい。State（移動／待機など）と、区間・待機理由・遷移条件を組み合わせて表現できる。

## 4. 横断歩道：代表的な State 遷移

1. `SidewalkWalking` の ID が横断歩道入口に到達して進入を要求する。
2. 歩道歩行 State のままでは横断歩道へ入れないため要求が不成立となり、`CrosswalkWaiting` に遷移する。
3. **横断開始前にのみ**信号の青／赤をチェックする。赤なら信号変化イベントを待つ。青なら入場可能な ID が `CrosswalkWalking` へ移る。
4. 青になったイベントで、同じ横断歩道を待っている ID 集団をまとめて再開する。
5. 横断開始後は、通常の信号サイクルが赤に変わっても途中で止めずに渡り切る（例外的な通行止め等は別ルール）。
6. 横断歩道終端で歩道への進入を要求する。`CrosswalkWalking` のままでは区間条件と一致しないため、`SidewalkWalking` へ遷移して歩道上の移動を続ける。

この「不成立 → State 遷移」という表現を仕様として使う。再度経路を探索する必要のない場合、ここでいうリルーティングは **状態・区間への振り分け** を意味する。

### 車と歩行者

車両は横断歩道などの進入境界で、歩行者の通行状態や信号・優先関係を問い合わせる。歩行者の通行により入れない場合は `WaitingForPedestrian` に遷移し、条件が変わったときに再試行する。

判定を車 1 台ずつ毎フレーム繰り返さず、境界の進入可否と待機 ID 集団を共有する。実際の停止位置、車間距離、渋滞長など、都市の交通状態へ影響する制約は、遠方でも簡略モデルで維持する。

## 5. 時間的 LOD：次に必要な時刻まで進める

例：曲がり角の手前にいる ID 群を、遠方ではまとめて **5 秒分** 進める。5 秒後に曲がり角へ到達するなら、その時刻に「右折する／直進する／横断する」判定を予約する。

~~~text
t = 100.0 秒   共通移動計算、到達予定時刻 105.0 秒を予約
t = 100〜105   定期的な個別移動更新は省略
t = 105.0 秒   対象 ID の境界判定 → State・所属集団を更新
~~~

**5 秒間隔の更新と「必ず 5 秒待つ」は違う。** 仮に 103 秒で別のイベントや境界に到達するなら 103 秒で処理する。計算の粗さによって重要な変化を見逃さないことが条件。

- 近距離: 描画に必要な位置、個体表現、必要な局所相互作用を高頻度で計算。
- 中距離: 連続計算を簡略化し、境界やイベントを優先。
- 遠距離: 次の境界・待機解除まで移動を予測して、イベントを予約し休止。
- カメラが移動するとき: 現時刻と基準状態から位置を復元し、突然飛んだり、二重に移動したりしない。
- 条件が変わったとき: 道路閉鎖、混雑の変化、経路変更等の影響範囲で予測イベントを無効化し、必要な部分を再予約。

実装候補は時刻順イベントキューやタイミングホイール。どちらを選ぶかは実測で判断する。同時刻イベントの決定的な処理順序も決める。

## 6. 移動計算と物理・描画の分離

- **論理移動（Process）**: 区間・速度・到達・進入条件・容量・State 遷移。画面外でも都市の整合性を維持する。
- **必要な詳細な相互作用（Process）**: 衝突回避や車間・歩行者の混雑等のうち、通行可否・交通量・所要時間などゲーム結果に影響する判断。
- **表示上の補間とアニメーション（UI）**: 状態を見えるようにする。描画の都合で論理的な通行判定を決定しない。
- **保存と復元（Data）**: ID・State・時刻・集団・予約などの永続化。ゲームルールを判断しない。

「描画範囲内のみ個別計算」は、主として**詳細な位置・物理表現を可視範囲へ限定する**という意味。画面外の交通容量や通行可否を省く意味ではない。カメラ操作だけで都市経済・混雑・実際の到達結果が大きく変わらないことを優先する。

## 7. 不変条件

- ID の一意性と同一性が保たれる。
- 移動・State 遷移で住民や車両が重複生成・消失しない。
- 分割前後で ID 集合と人数が一致する（明示的な生成・消滅イベントを除く）。
- 予約時刻以前に境界を無断通過しない。途中イベントで必要なら予測を取り消す。
- 信号の開始前判定、移動開始後の継続など、決めた State の意味が画面内外で一致する。
- 同一入力・同一乱数 seed・同一イベント順で、論理シミュレーションを再現できる設計を目指す。
- 描画 FPS と論理時刻の進行を結合しない。

## 8. 最初の実証と評価

最初から街全体を実装しない。歩道、横断歩道、信号、曲がり角、車両の通行待ちを持つ小さなマップで、まず State 遷移を検証する。

テスト観点：

1. 赤信号で 1,000 ID が待機し、青イベントで入場可能な ID だけ再開する。
2. 横断途中で赤に変わっても停止せず、終端で歩道歩行に戻る。
3. 右折する ID と直進する ID を集団から正しく分割できる。
4. 5 秒先の予測中に 3 秒後の重要イベントが入ったら見落とさない。
5. カメラを切り替えても人数、位置の整合性、経路結果が保たれる。
6. 進入競合時も容量・優先度を守り、ID が重複しない。
7. 人口 1 万／10 万／100 万、イベント密度の異なる条件で、CPU 時間、メモリ、GC、イベント数、集団分割数を測定する。

比較対象ゲームに対する優位性を断定せず、**都市規模・集団数・イベント頻度・可視個体数に対して何が負荷を支配するか**を計測する。

## 9. UPD との関係

本設計の論理シミュレーションとルール判断は Process。入力や描画は UI。セーブ・ロード等の取得／保存は Data。

責務の境界は [UPD Design](https://github.com/tomiya7688/upd-design) および [コーディングルール](CODING_RULES.md) に従う。UI と Data を直結しない。
