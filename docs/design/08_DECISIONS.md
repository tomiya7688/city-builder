# 8. 設計判断・リスク・未確定事項（CB-SDD-08）

> **この章は設計の決定と、実測が必要な部分の境界を明確にする。** 「全部設計済み」と書くために根拠のない細部を確定しない。記録のない暗黙の例外は設けない。

## 8.1 確定した設計原則（ADRベースライン）

| ADR | 決定 | 理由 | 検証/関連 |
| --- | --- | --- | --- |
| ADR-001 | 個体数とオブジェクト数を一対一に強制しない | ID同一性は必要だが、処理は共通化できる | #61, S-001 |
| ADR-002 | 正規のWorldStateはProcessだけが所有する | カメラ/IO/Workerによる状態分岐を防ぐ | #65, S-011 |
| ADR-003 | Groupは正規Stateの派生索引とする | 分割/統合・保存/復元で個体を失わない | #61, S-001/002 |
| ADR-004 | 移動予測と境界進入判定を分ける | 次の判定時刻まで個別更新を休止するため | #64, S-002〜005 |
| ADR-005 | 信号・容量・待機解除はイベントで処理する | 全員の毎フレームポーリングを避ける | #62/#64, S-003〜010 |
| ADR-006 | 同時刻イベントは(microRound,phase,sequence)順 | 競合/保存・再生結果の一貫性を保つ | #62, S-004/009 |
| ADR-007 | 早着/遅延の双方で到達イベントを再予約する | 古いイベントを無視するだけでは早着を逃す | #62/#65, S-006/007 |
| ADR-008 | 交通量・容量・経済・人口を可視性に依存させない | カメラ位置で都市結果が変わるのを防ぐ | #65/#66, S-011 |
| ADR-009 | UI/Process/Dataの責務を厳守する | ゲーム判断、表示、入出力を混ぜない | #67, NFR-08 |
| ADR-010 | 具象final、具象継承禁止、独自オーバーロード禁止、移譲を守る | 実装の責務と契約を明確にする | [CODING_RULES](../CODING_RULES.md) |
| ADR-011 | 完成版はPC向けオフライン3Dの街づくりゲーム | 都市シミュレーションの性能/操作を優先 | [GAME_DESIGN](../GAME_DESIGN.md) |
| ADR-012 | データ駆動テンプレート、任意コードModは初期v1対象外 | 施設種類をクラス数へ直結しない、安全な拡張 | #71 |
| ADR-013 | セーブは版付きチャンクの明示スキーマ | JVMオブジェクト内部構造から切り離す | #59, P-001〜005 |
| ADR-014 | まず単一の決定的State確定スレッド | 順序依存バグを防ぎ並列化を後から検証 | #3/#62/#67 |

**実装方法の採用案（確定済みの規約ではない）**と、上記の**必須設計契約**は区別する。

## 8.2 先に試す技術構成（採用案）

| 項目 | 初期案 | 採否の判断基準 |
| --- | --- | --- |
| JVM | Java 21 LTS、Kotlin | 3OSビルド、JIT/GC、API相互運用 |
| ビルド | Gradle Kotlin DSL | 再現可能なバージョン固定、CI |
| 表示 | libGDX + LWJGL3 | 3OSでのOpenGL経路とチャンク描画、ゲームルール非依存 |
| 移動の到着索引 | Group内ヒープ/時刻バケット等 | 最早到着、分割/再アンカー、メモリ/CPUの比較 |
| Globalイベントキュー | PriorityQueue＋取消/再構築 | 同時刻の安定順序、無効イベントの蓄積抑止 |
| 動作時のIDデータ | `LongArray`等の内部表現の候補 | 参照整合・GC/メモリ性能、公開APIカプセル化 |
| 乱数 | seed/ID/purpose/occurrenceで決定的な値 | イベント並列度・カメラによる差なし |
| 保存 | 版付きチャンク形式 | 形式検証、セーブ/ロード、互換性と性能 |
| 並列化 | 状態確定以外の純粋計算・描画・I/O | 順序不変、負荷で有益な場合のみ |

**これらが未実装であること**と、ソフトウェア設計に採用する原則が明確であることは矛盾しない。

## 8.3 リスク登録簿

| ID | リスク | 兆候 | 緩和策/実証 |
| --- | --- | --- | --- |
| RK-01 | 個体差が多すぎGroupが細分化し共有効果が減る | Group数がID数に近づく | 共通規則を共有し最早到着索引を計測。低共有率の性能試験 |
| RK-02 | 大量の旧イベント・失効予約がヒープを圧迫 | EventQueue実要素≫有効件数 | 取消・compaction・失効率の計測 |
| RK-03 | 道路の循環待機でグリッドロック | 進入待ちが長期固定 | 相互待機検出・警告・再探索。テレポートしない |
| RK-04 | 大都市の経路探索にCPUを使い切る | OD再探索/区間変更が爆発 | 階層経路・ODキャッシュ・影響逆引きを比較 |
| RK-05 | 停電↔ポンプ↔需要の変化で無限再評価 | 同時刻microRoundが増大 | 版/閾値/ヒステリシス、周期境界で収束 |
| RK-06 | セーブSnapshotの複製にメモリを使いすぎる | 保存時のヒープ/GCピーク | Chunk単位Snapshot、copy-on-write、保存中の並列I/O |
| RK-07 | JVM/OSごとの浮動小数順で再現性が崩れる | 異OSのWorldStateハッシュ不一致 | 時刻/元帳/容量を整数中心とし、演算順と丸めを固定 |
| RK-08 | 地形・3D描画がCPU/GPU負荷を支配 | FPSが都市人口とは無関係に低い | チャンクLOD/instancing/可視密度をUI側で最適化 |
| RK-09 | 税・需要・成長が振動し都市が不自然 | 急激な全住民転出/供給反転 | 平滑化/継続日数・閾値・原因表示とプレイテスト |
| RK-10 | libGDXと厳格な具象継承禁止が衝突する | 必須APIが具象継承を要求する | interface/adapter/委譲で回避し、困難ならライブラリ見直し |
| RK-11 | UPD自動検査の言語対応が不十分 | Kotlinは検出できてもJavaの全参照を見逃す | #67で静的解析を補強し、人手レビューも必須 |
| RK-12 | セーブ更新で旧都市データが壊れる | 互換版で施設参照が欠落 | versioned schema・マイグレーション・バックアップ・P系試験 |

リスクは「開発課題」だが、ゲーム内の状態整合性と保存の安全を犠牲にして解決しない。

## 8.5 仕様の版と変更ルール

- 要求・ゲームルールを変える場合：`GAME_DESIGN`/対象分野文書→このSDDの関係章→関連Issue/テストIDを同じ変更で更新する。
- IDやイベント順を変える場合：`RUNTIME_PROTOCOL`/このSDD第3〜4章→セーブ/再現テスト→関連Issueを同時更新する。
- 数値だけ変更する場合：`QUANTITATIVE_MODEL`/`GAME_BALANCE_RELEASE`のデータ版、理由、プレイ結果を記録する。
- JVM/描画方式を変える場合：`TECH_STACK`/第2章/第6章の互換性/OS試験を更新する。
- 性能目標に届かなかった場合：実測を残してIssueに改善策を記載。**目標値を事後的に下げて達成済みにしない**。公開の可否と目標の見直しは別の設計判断とする。
