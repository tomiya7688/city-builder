## 目的と読み方

## 正本と優先順位

不一致がある場合は、まず意図を確認して関連文書を**同じ変更で修正**する。「新しいファイルが無条件で勝つ」とはしない。責務ごとの一次資料は以下。

1. **ゲームの完成要件・機能と見た目** — [GAME_DESIGN](../GAME_DESIGN.md) と [プレイヤー体験](../PLAYER_EXPERIENCE.md)、機能分野別文書。
2. **ID・論理時刻・イベントの共通的な意味** — [RUNTIME_PROTOCOL](../RUNTIME_PROTOCOL.md)。本書第4章はその実装構造を定義する。
3. **State・条件イベントの種類** — [STATE_EVENT_CATALOG](../STATE_EVENT_CATALOG.md)。本書はデータ表現・処理手順・失敗時の扱いを補う。
4. **ゲームバランスの初期値** — [GAME_BALANCE_RELEASE](../GAME_BALANCE_RELEASE.md)、[QUANTITATIVE_MODEL](../QUANTITATIVE_MODEL.md)。数値の調整と単位整合はここに記録する。
5. **OOP/UPD必須規約** — [CODING_RULES](../CODING_RULES.md)、外部正本の[upd-design](https://github.com/tomiya7688/upd-design)。本書が例外を暗黙に認めることはない。
6. **タスクと対応する検証** — [設計対応表](../DESIGN_TRACEABILITY.md) と各Issue。

## 固定するアーキテクチャ原則

- ゲーム内個体の**同一性はIDで保持**する。オブジェクト数を人口数に合わせる／合わせないこと自体は目的にしない。
- **同じ計算の実行を共有**し、IDごとの到達・進路・属する施設とStateは失わない。
- **正規状態はProcessにのみ存在**し、集団は計算を共有するための派生索引、描画は非権威的な投影。
- 区間内の予測移動と、境界への進入リクエスト・State切替・容量確保を**別責務**にする。
- 必要なイベントの時刻だけ確定処理を実行する。遠方/不可視の定期更新は削減しても、重要な境界イベントや容量制約は省略しない。
- UI/Process/Dataを分離する。**UI↔Dataの直接経路を禁止**し、Processがルール、DataがI/O、UIが入力・表示を担当する。
- 具象クラスの継承・独自オーバーロードは禁止。`final`、移譲、1クラス1責務、1関数1処理、制御ネスト最大2段、カプセル化を遵守する。

## 仕様のステータス

表記を統一する。

| 表記 | 意味 |
| --- | --- |
| **必須** | 実装・受入試験で守る契約 |
| **初期採用案** | まず作る方式。試験で不都合が判明した場合のみ変更を審議 |
| **調整値** | JSON等のデータで持つ係数・上限・閾値。ゲームバランスと性能試験で変更可 |
| **未確定** | 根拠・比較試験が必要。Issueを割り当て実装前に判断 |
| **実装済み** | コード・試験・リポジトリのコミットで確認できた場合のみ使用する |

**現在はすべて文書上の設計であり、実行可能なコアや100万人の性能は検証済みではない。**

## 完了までの責務

本書が満たされるだけではゲームは完成しない。各Issueの実装、コアの状態整合試験、都市機能のE2E、日英UI、保存/ロード、3OS QA、実測性能、配布物署名・真正性確認（既存 #1）を終えてはじめて「完成したゲーム」と判定する。

更新時は本書の変更対象章、対応する仕様正本、関連Issue、テストケースIDを必ず示す。
