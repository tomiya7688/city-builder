# 7. 試験仕様・品質ゲート・トレーサビリティ（CB-SDD-07）

> **試験設計であり、試験結果ではない。** 全テストは未実行。既存の [VALIDATION_PLAN](../VALIDATION_PLAN.md)、[GAME_BALANCE_RELEASE](../GAME_BALANCE_RELEASE.md)、[#66](https://github.com/tomiya7688/city-builder/issues/66)、[#76](https://github.com/tomiya7688/city-builder/issues/76) を具体化する。

## 7.1 試験のレベル

| レベル | 対象 | 外部依存 |
| --- | --- | --- |
| Unit | ID生成、Group分割、移動時間、容量、税・在庫などの純粋計算 | 不変入力とテスト用時計のみ |
| Component | Processのイベントキュー・Boundary・建築/人口Domain | Rendererなし、Dataはテストアダプタ |
| Integration | 道路→住宅→住民→通勤→税、停電→施設停止など | Processの複数Domainを実際に結合 |
| End-to-end | UI入力からゲーム世界変更、情報表示、セーブ/ロード、シナリオ達成 | 選定した描画基盤とData I/O |
| Property/Replay | 大量のランダムなイベント系列、State不変条件、固定seed再生 | ヘッドレス、出力の正規ハッシュ |
| Benchmark | 1万/10万/100万ID、実都市に近い経路/需要負荷 | CPU/GC/メモリ計測、Rendererを個別評価 |
| Release QA | 3OS、コンテンツ、日英、アクセシビリティ、配布署名 | 実配布物・実機 |

**優先順は正しさ→再現性→性能**。速くてもIDが消えたり赤信号で進入する場合は不合格。

## 7.2 Phase0の決定的なfixture

試験データは次の条件を固定して配布する（このファイルに結果が存在するわけではない）。

- `worldSeed = 123456`（テスト用。製品の実ゲームseedを制約しない）。
- 単位：距離m、速度m/SimClock秒、時刻ミリ秒、容量は人数/車両。
- Segment A（100m）→横断歩道X（5秒）→Segment B。道路R/Sと競合領域C。青/赤は明示したイベント列で発生。
- 1000人試験では`CitizenId=1..1000`、次の時刻順は`(scheduledAt, microRound, phase, stableSequence)`。
- UIのカメラ/レンダラーは試験条件でON/OFFし、Processの入力コマンド列は一致させる。

### キャッシュとイベントの非依存試験

移動計算の共有群を、意味を変えずに2Groupへ分割して実行した場合と、一つのGroupで実行した場合の**正規世界の結果**が同じになることを検証する。GroupId/内部メモリ配列順は比較対象から除外する。入力seed、ルール版、予定コマンドは同じにする。

## 7.6 ベンチマークの設計

### 同じ負荷で比較する

- Baseline A：全IDの定期位置更新方式（正しさを同じとする比較用）。
- Approach B：共通移動規則＋Group内の最早到着バッチ＋グローバルイベントキュー。
- Approach C：Bにさらに時間帯/地区/需要の集約・局所失効を加えた実装。
- **都市負荷は単に100万個のIDを保有するだけでなく**、通勤、交差点、電力・水道、仕事/税、建物、保存等が動くデータを使う。

| 設定 | 値/条件 |
| --- | --- |
| 個体数 | 10,000 / 100,000 / 1,000,000 |
| 移動共有率 | 低/中/高：同じ区間・速度・進路のID割合を変える |
| 信号/境界 | 少ない/多い、通勤ピークで多数待機 |
| 失効頻度 | 道路変更・渋滞改善・停電を少/多で変える |
| 可視数 | 0 / 数百 / 数千（描画ON時） |
| 経路 | 一本道・格子・高密度の交差点ネットワーク |
| 保存 | 保存なし/一定間隔、圧縮やI/Oの時間を別計測 |
| 実行環境 | JDK、CPU/GPU、RAM、OS、JVMオプション、ゲーム版、seedを記録 |

### 指標

CPU時間、wall time、イベント数、Group数、分割/統合数、失効/再予約数、最早到着索引の処理時間、状態確定のp50/p95/p99、GC回数/停止時間、ヒープ/割当速度、描画フレーム時間/draw call、セーブ処理時間。

- 初回JITウォームアップとコールド起動は分ける。
- 同条件を複数回実行し中央値/分布を報告。性能の比較で計算式や通行ルールを変えない。
- 比較グラフには**結果の正しさ**（Stateハッシュ/保存則）も併記する。
- エラーや遅延を見えなくする「イベントスキップで速くする」を評価上の性能向上と認めない。
- 10万/100万都市のFPS・メモリ・セーブ時間の目標値は [GAME_BALANCE_RELEASE](../GAME_BALANCE_RELEASE.md) の未検証の受入条件を参照する。

## 7.8 トレーサビリティと「完了」の根拠

実装Issueには少なくとも**要求ID・設計文書章・テストID・実行結果・実行環境・未検証事項**を紐づける。

- テスト計画が書かれているだけなら**未実行**。
- テストに成功したがシナリオを通していなければ、ゲーム機能は**統合未検証**。
- 100万人でFPSが出たが税や交通が動いていないなら、**大規模都市検証は未達**。
- 既存 #1 の署名・Artifact Attestation・配布物の真正性が未完了なら、**一般配布ゲートは未達**。

本書の全項目を「実装済み/合格」として報告するには、テスト結果のコミット・CI URL・再現コマンド等の証跡が必要である。
